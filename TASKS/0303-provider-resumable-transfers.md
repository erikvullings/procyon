# 0303 Provider byte-range and multipart resume

Status: done
Priority: medium
Subsystem: backend, remote
Depends on: 0299, 0300, 0301

## Context
Resume is a capability, not a promise. Providers that can prove a partial destination belongs to
the same job and source revision may continue instead of restarting. Parent: 0163.
Currently only OneDrive advertises `resumable_upload/download`; SFTP, WebDAV, S3, FTP do not.

## Acceptance Criteria
- Each provider that claims resume implements and tests it: SFTP (offset write on a job-owned
  partial), S3 (multipart upload ids with listed parts), WebDAV (ranged GET; PUT resume only where
  the server provably supports it); others stay `false`.
- Resume requires proof: the partial is job-owned (journaled name/upload id) and the source
  revision matches; otherwise the transfer restarts or needs intervention.
- Expired credentials, replaced partial, and stale source fall back safely and report why.
- Fault-injection tests per provider: disconnect mid-transfer, replaced destination, stale source,
  expired credentials, multipart recovery.
- `TransferCapabilities` advertisement matches implemented behaviour (no over-advertising).

## Agent Notes
- 2026-11-05 claude: Split from 0163. Needs the journal (0299) and classification (0300).
- 2026-11-06 claude: SCOPE CUT. Delivered the shared resume machinery and SFTP; S3 multipart and WebDAV were split into 0315 and 0316 (each needs protocol-specific work and its own fault-injection server). 0163 therefore stays open until those two are done.
- Provider API: `FileSystemProvider::open_write_at(partial, offset)` (default `UnsupportedCapability`; must not truncate, must refuse a missing partial with `NotFound` and an offset past the partial's end). SFTP implements it (the partial's length must EQUAL the offset: shorter would leave a hole, longer a stale tail) and `read_range` over SFTPv3 `seek`, and now advertises `random_read` and `random_write`. It deliberately does NOT set `resumable_upload`/`resumable_download`: the planner reads those as Graph-style sized upload sessions and would add a source `stat` to every SFTP copy. No other provider claims offset I/O; OneDrive's existing flags are unchanged.
- Engine: `OperationsCoordinator::start_resuming` / `OperationPlanner::plan_with_resume` take hints (source file -> partial). `CopyExecutor::try_resume` PROVES the partial instead of trusting the journal: the provider can append, the partial exists, it is non-empty and not longer than the source, and its bytes equal the first N bytes of the CURRENT source (`compare_copy` with a limit). Only then does it open the source at offset N (`read_range`, else read-and-drop the prefix), open the partial with `open_write_at`, count N bytes as already done, and continue; the usual verification (0302) and publish steps follow. Any failed proof discards the partial and copies from the start, recording one of `resumeFallbackPartialGone` / `SourceChanged` / `PartialMismatch` / `Unverifiable` (an empty partial is replaced quietly); a clean resume is only logged (it must not turn a good copy into "completed with warnings"). A resumed file is always verified (0302) before it is published, because the source is re-read for the tail after the prefix was proven. A failure to CHECK the partial (dropped link, cancel) is not evidence against it: it propagates for the retry and leaves the partial in place; only a proven mismatch, a changed source or an unusable provider discards it. Strings in all 8 locales.
- Recovery (0300): `Resumable` is now produced, when the destination provider can append, the partial holds some bytes but not more than the source, and the source looks unchanged. `restart(resume=true)` hands the proven partials to the new run (and keeps them), removes the other partials, and refuses with `invalidRequest` when nothing can be resumed. REST `POST .../restart?resume=true`, Tauri `restart_interrupted_transfer(resume)`, all three clients, and a "Resume" button next to "Run again" on resumable transfers.
- Trade-off to know: the proof re-reads the partial (N bytes from the destination) as well as the source, so resuming saves the UPLOAD of N bytes, not the read-back. That is what makes it safe without byte checkpoints in the journal, and it is the right trade on the usual asymmetric link.
- Verified: real in-process SFTP server (fm-vfs-sftp): `read_range` slice/offset, `open_write_at` continues without truncating, refuses a missing partial and a hole; 8 engine tests with an appending provider double (resume, foreign prefix, source shorter than partial, missing partial, provider that cannot append, empty partial, verified resume, cancel during proof); 6 coordinator tests (offer, not offered without append or when longer/empty, hand-over keeps the partial, plain restart still discards, mixed items); 4 frontend tests. Workspace `cargo clippy` clean; `cargo nextest run` on the touched crates 1793 passed.
- Also fixed: the 0300 test fixture created its job "now" after writing files, which made one freshness test flaky at millisecond boundaries.
- Known gaps: no single test drives `CopyExecutor` against the live SFTP server (the provider is tested against it and the engine against a double); the journal does not record a resume token, so providers whose partial is not a plain appendable file (S3) need 0315; a retry (0301) after a resumed attempt discards the partial and restarts that file; the offer ignores a changed source when no revision was journaled (local sources), relying on the byte proof at resume time.
- Review follow-ups applied: partial kept on transient proof failure; SFTP no longer advertises the sized-upload flags; `open_write_at` requires an exact length; clean resumes are not recorded as warnings; resumed copies are verified. Left open: (a) a partial handed to a resumed run that never reaches that item (cancelled early, skipped by policy) stays on the destination, because the interrupted-transfer record is dropped when the new run starts; (b) the already-sent prefix is reported as one `report_bytes(N)` at the start of the item, so speed/ETA spike briefly; (c) the source re-read after the proof can still change in that window, which the forced verification catches before publishing; (d) the offer checks size only, relying on the byte proof for same-size edits.
- 2026-11-06 claude: LIVE VERIFICATION against real servers (podman, one-off; containers, images and temp files removed afterwards): OpenSSH (`linuxserver/openssh-server`), S3 (SeaweedFS), WebDAV (`hacdias/webdav`, Go `x/net/webdav`). The ignored tests are `operation_planner::tests::live::live_*` (see the module doc for the servers they expect; run with `cargo nextest run -p fm-application --run-ignored only live_`). Results: SFTP upload AND download resume pass end to end with verification; S3 and WebDAV DOWNLOAD resume pass (S3 over a ranged `GetObject`, WebDAV by reading and dropping the prefix because the WebDAV provider has no `read_range`); S3 and WebDAV UPLOAD correctly fall back to a full copy and still publish the right object.
- To make downloads resumable the LOCAL provider now implements `open_write_at` (exact-length contract) and advertises `random_write`. The recovery offer additionally requires the two backends to differ (a same-backend copy is provider-native and never streams, so a partial there could not be continued), and a hinted partial that the copy will not use is discarded instead of left behind.
- BUGS FOUND BY THE LIVE RUN AND FIXED: (1) the S3 and WebDAV upload writers returned from `shutdown()` before the server had finished (the code even documented it) and dropped the upload's result, so the engine's next step raced the upload (404 on S3's server-side copy, 423 on WebDAV's MOVE) and a refused upload was never reported. New `fm_vfs::upload_pipe`: `shutdown` now waits for the upload task's verdict and fails with its error (a dead pipe on write reports the upload's own reason). Used by S3 and WebDAV; FTP has the same bare-duplex pattern and was NOT changed (no live FTP server in this run). (2) A regression from 0299: the scheduler awaited the journal's `finish` at the end of every job, which kept the scheduler and history writer alive past the service, so a quick restart read a history file without the job's terminal snapshot (`restart_preserves_the_evidence_needed_for_undo` failed about half the time). Removal is now queued (`OperationJournal::discard`) instead of awaited; the test passed 40 of 40 runs afterwards. Bisected: 0 of 25 failures before 0299, about half after.
- What this does not cover: S3 multipart-upload resume (0315) and WebDAV upload resume / ranged GET (0316) remain open; FTP resume and FTP's upload-completion race are untouched.
