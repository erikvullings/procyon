# 0258 Directory refresh amplification (large dirs, post-operation)

Status: open
Priority: high
Subsystem: backend, frontend
Depends on: 0156

## Context
Navigation/refresh feels slow in the Tauri app. Profiling by code reading plus `fm-vfs-local` bench (2026-10-18): raw listing is cheap (10k entries stat+list ≈ 15 ms, 100k read_dir ≈ 52 ms), so the cost is repeated work and IPC round trips, not the filesystem or webview.

Findings (file refs):
1. `LIST_PAGE_SIZE = 256` (`crates/fm-application/src/directory.rs:55`) is also the delta threshold in `deltas_for_change`: any directory with >256 entries never gets incremental deltas, only `Reset` with page one.
2. Frontend `applyDelta` (`frontend/src/app/app-shell.ts` ~2090) answers a Reset with `hasMore` (or any delta while `current.hasMore`) by `refetchAffectedPanes` -> `navigation.load` -> backend `list()` with no continuation token = a second full relist + sort, then `hydrateBackgroundSnapshot` fetches remaining pages serially (`navigation.ts` ~453). Result per fs event in a big folder: watcher relist + frontend relist + N/256 sequential IPC calls.
3. Operation completion triggers three refreshes per affected pane: backend `refresh_affected` (ResetRequired relist), frontend foreground `refetchAffectedPanes` (`panesNeedRefresh` in `backend-event-handler.ts`), and the FS watcher's own relist.
4. `list()` cost per continuation page: `provider.inspect` writability stat and `aggregate_totals` over the full list on every page (O(n^2/256)); `publish_changes` clones the page/snapshot several times and re-sorts the full list each event.
5. `hydrateBackgroundSnapshot` re-spreads `mergedEntries` per page (O(n^2/256)); `applyDelta` rebuilds a Map of all entries and appends added entries unsorted (verify whether the table re-sorts client-side).
6. Watch debounce (75 ms, `fm-vfs-local/src/lib.rs`) is leading-edge only; bursts still relist repeatedly.

## Acceptance Criteria
- Measure first: add `performance.mark`/Rust `tracing` spans for navigate -> first paint and fs-event -> repaint; record baseline for 300, 10k, 100k-entry dirs in this file.
- Large directories use incremental deltas (diff against full cached list) or a single bounded Reset; no frontend relist on a normal delta.
- Frontend never triggers a full backend relist in response to a backend-originated delta; remaining pages are served from the cached `full_entries`.
- One refresh per affected pane per operation (dedupe backend reset, watcher event, and frontend refetch).
- Continuation pages skip the writability stat and totals recompute (cache in `PaneRequest`).
- Trailing-edge debounce/coalescing of watch bursts; before/after numbers recorded; `pnpm test` and `pnpm lint` green.

## Implementation Notes
- Keep logic in `DirectoryService`; keep Tauri/Axum handlers thin. Preserve browser/Tauri parity.
- Consider binary/compact transport for pages if IPC serialization shows up in the traces.

- 2026-10-18 (pass 5, ROOT CAUSE of slow delete + part of slow startup): real-app run showed single-file delete = queued->planning->running->completed with ~300 ms between EVERY state transition (backend `queue_to_start_ms=314`, `created_to_completed_ms=890`; `op-start-request` -> `op-start-returned` 316 ms), ~1.2 s from keypress to repaint, while the filesystem work and relist are ~10 ms. Cause: `OperationHistory::observe` ran `prune_and_save` synchronously on the scheduler thread for every transition: pretty-JSON of up to 100 operations + temp file + `sync_all()` (full fsync, ~300 ms on macOS) under the history lock. The same `fsync` also ran in `OperationHistory::load` during `FileManagerService` construction (startup `service-constructed` phase took ~450 ms of the 667 ms before the first window).
- Fix: write-behind `HistoryWriter` thread in `operation_history.rs` — transitions only mark dirty; the thread coalesces bursts into one durable (fsync'd) write of the latest snapshot; `Drop` drains it. Durability semantics unchanged except a crash within ~one write after a transition can lose that transition (in-flight ops are restored as Interrupted on load anyway). Tests: 3 new in `operation_history::tests`; full `fm-application` suite green (1010).
- Remaining startup budget (dev build): window created ~0.67 s after process start, then ~1.1 s of webview/Vite/JS boot before the first `list_directory` call (`fm:list-ipc @1126`), first paint @~1.2 s. Re-measure after pass 5 and compare with a release build before touching the frontend boot.
- 2026-10-18 (pass 6, after write-behind history): delete/copy `queue_to_start_ms` 314 -> 1 and `op-start-request`->`returned` 316 -> 15 ms (fsync fix confirmed). Still ~300-350 ms from start to terminal (`created_to_completed_ms` 309 delete / 351 copy) for a single file whose FS work and relist are ~10 ms, so another ~300 ms stage remains inside `Scheduler::run_job` (suspects: `executor.plan`, `executor.finish`, `executor.undo_evidence`, event delivery batching). Added `fm_perf op=run_job` with cumulative `transition_ms/planned_ms/executed_ms/finished_ms/undo_evidence_done_ms` to locate it.

- 2026-10-18 (pass 7, ROOT CAUSE of the remaining ~310 ms): `fm_perf op=run_job` showed `transition_ms≈310` (the Queued->Planning transition) with plan/execute/finish all <5 ms. Cause: `~/Library/Application Support/procyon/operation-history.json` was **19 MB** — one cancelled delete of `~/.cache` (5.7M planned items) stored 38,711 per-entry errors (15 MB). Every history save serialized/cloned/fsynced that file, and the `operations` mutex was held during serialization, so the scheduler's next `observe()` blocked ~300 ms (debug build; release is faster, hence "indeed faster" in the installed app). This also explains the earlier fsync cost.
- Fix: (1) writer snapshots the history under the lock and serializes/writes outside it (`HistoryWriter`); (2) per-operation persisted `errors` capped at 200 + one summary entry ("N further errors are omitted from the saved history"), applied in `observe` and on `load` so the existing 19 MB file shrinks on next start; (3) new `fm_perf op=history_save` timing. Tests added; `fm-application` suite green.
- Note for follow-up: the scheduler keeps ALL 38k errors in memory and emits them in operation payloads while an operation runs; consider capping live errors too (separate task if it shows up in profiling).
- 2026-10-18 (pass 8, verified in the dev app): single-file permanent delete `created_to_completed_ms` 890 -> 16 ms (copy 351 -> 69 ms); `run_job transition_ms` 310 -> 0.08 ms; `operation-history.json` 19 MB -> 289 KB; background `history_save` 12-25 ms, off the scheduler thread. Startup `windows-created` ~613 ms (dev build). Listing paths unchanged (~11-13 ms backend for 932 entries).
