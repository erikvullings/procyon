# 0150 Video playback in the F3 Lister viewer

Status: done
Priority: low
Owner: unassigned
Agent: copilot
Area: frontend
Depends on: 0088

## Context

Raised during the 2026-08-19 ForkLift feature-gap discussion: the Lister viewer (0088) already
plays audio via a native `<audio>` element fed a whole-file `data:` URI
(`readFullAudioDataUri`/`renderAudioBody` in `frontend/src/features/preview/content-preview.ts`
and `file-viewer.ts`), but there is no equivalent `'video'` `PreviewKind` — `resolvePreviewKind`
only recognizes `text`/`image`/`audio`/`pdf`/`comic`/`epub`/`metadata`. `VIDEO_EXTENSIONS` already
exists (`frontend/src/features/directory-table/entry-icons.ts`, used today only for icons/
thumbnails), so the extension list is ready; the viewer path is not.

**Mirroring the audio pattern exactly is genuinely easy** — a `'video'` `PreviewKind`, a
`videoMimeTypeFor` alongside `audioMimeTypeFor`, and a `renderVideoBody` that swaps `<audio>` for
`<video controls>` — and works fine for short clips. It is **not** a drop-in for video in general:
`readEntireFileBytes` (shared by the image and audio paths) has **no size cap** by design — "full
images/audio are always loaded, per Total Commander convention" (its own doc comment) — because
those are normally small. Video files routinely run into the hundreds of megabytes to several
gigabytes; loading one whole-file into memory as a base64 `data:` URI (~33% size inflation on top)
would be a real regression, not a quick win, for anything but short clips. This task should not
silently inherit the audio path's no-cap behavior for video.

## Acceptance Criteria

- New `'video'` `PreviewKind` in `resolvePreviewKind` (`content-preview.ts`), matched against
  `VIDEO_EXTENSIONS`.
- `renderVideoBody` in `file-viewer.ts`, structurally mirroring `renderAudioBody`: a native
  `<video controls>` element (the standard HTML5 Media API — no third-party player library).
- A file-size threshold below which the existing whole-file `data:`-URI path is used unmodified
  (reusing `readEntireFileBytes`, same as audio/image today) — this is the "easy" F3 View
  extension the task is named for, and should land as a self-contained first step.
- Above that threshold, the viewer does **not** attempt to load the whole file. At minimum: show a
  clear "large video — external playback only" state with an action to open it in the OS default
  player (reusing the existing `core.open`/`open_with_default_application` path), rather than
  hanging or exhausting memory. A true in-app streaming/seekable path (Media Source Extensions fed
  by chunked `readFileRange` calls, or a Tauri-only local-file-protocol fast path) is explicitly
  **out of scope** for this task — flag it as a follow-up task if there's real demand, per this
  project's own precedent of not over-building preview renderers speculatively (see 0071's Agent
  Notes on PDF/CBR: "flag for product input before scoping renderer work" rather than assuming).
- Tests: `resolvePreviewKind` returns `'video'` for `VIDEO_EXTENSIONS`, `renderVideoBody` renders
  a `<video>` element with the correct `src`/MIME type for entries under the threshold, and the
  "open externally" fallback path is exercised for entries over it.

## Implementation Notes

- `videoMimeTypeFor`: mirror `audioMimeTypeFor`'s extension→MIME table (`mp4: video/mp4`,
  `mov: video/quicktime`, `webm: video/webm`, `mkv` has no universally correct browser-safe MIME —
  decide whether to attempt one or route `.mkv` straight to the "open externally" path regardless
  of size, since browser `<video>` support for MKV containers is inconsistent even when the codec
  inside is supported).
- Pick the size threshold pragmatically (e.g. reuse `PREVIEW_SIZE_LIMIT_BYTES` or a separate,
  larger video-specific constant) and document why, rather than picking an arbitrary number
  silently.
- If a poster/thumbnail frame is already generated by 0134's video-thumbnail pipeline, wire it into
  the `<video poster>` attribute for a nicer loading state — check what 0134 already produces
  before adding new thumbnail-generation code.
